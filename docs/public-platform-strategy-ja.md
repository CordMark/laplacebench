作成: 2026-07-21。「多くの人がこのベンチマークに触れられる土台」の設計。
研究戦略([benchmark-strategy-ja](benchmark-strategy-ja.md))と実験計画
([experiment-axes-ja](experiment-axes-ja.md))の上に載る、配布・参加・
観戦の戦略。

> **スコープ注記 (2026-07-30 更新)**: Model Arena は引き続き
> **モデルのベンチマーク**に絞る。保留していた「固定モデル・自由設計」は
> Harness Lab 内の controlled division 候補として残し、全体は各陣営が
> harness × model ペアを選ぶ別タブ **Harness Lab** として方向設計を再開した。
> 本書の旧シーズ案に優先して、名称、許可階層、投稿/対戦の未決定事項は

## 0. 一行の定義

**「誰も知らないボードゲームで、フロンティアモデルを戦わせる公開アリーナ」**

触れる人ごとに違う顔を持つ:
観戦者にはeスポーツ、開発者には遊べるSDK、研究者には再現可能な評価基盤。
(harness × model ペアを競わせる別 Harness Lab は方向設計中。
固定モデル戦はその中の controlled division。公開されれば4つ目の顔になる)

## 1. 参加の階段(ファネル)

現行は深さ順に4段。各段の摩擦を最小化する。

| 段 | 人 | 体験 | 必要なもの |
|---|---|---|---|
| 1. 見る | 誰でも | 公開ビューワーで名勝負を観戦、リプレイURLを共有 | ブラウザだけ |
| 2. 回す | Claude/ChatGPT加入者 | `npx laplacebench` で自分のサブスクを使い5分で初対局 | 既存サブスク |
| 3. 実験する | 開発者 | 条件を変えて走らせる(モデル、effort、観測形式)。ローカルの対局を公開ビューワーにドラッグ&ドロップで再生 | 同上 |
| 4. 提出する | コミュニティ | 対局ログをPRで提出 → CIがリプレイ検証 → コミュニティ台帳に載る | GitHub |
| 5. ハーネスを実験する | 開発者/競技者 | **一部実装済み(2026-07-31)。** 同梱の3条件(persistent / reset / memo)は今日からセルフサーブで実行可能(clean-room 既定・公開 matchup には不混入)。**自作ハーネスの投稿・挑戦**は未決定(declarative pack が有力候補、[Harness Lab 方向性 §5](harness-lab-direction-ja.md)) | 既存サブスク |

設計原則: **上の段ほど摩擦ゼロに、下の段ほど検証を厚く。**

段3の「条件を変える」は Model Arena 内のモデル側の条件を指す。
ハーネスを差し替えた対局(`claude-cli-learn` など)は Harness Lab 側の候補で、
モデル対モデルの記録とは混ぜない。現在の公開カタログにはまだ載せない。

## 2. サブスク問題の答え: 3レーンの信頼モデル

「全部個人サブスクで回している」は弱点ではなく、レーンを分ければ
そのまま配布戦略になる。

### レーンA: セルフサーブ(BYOサブスク)
個人が自分のClaude Code / Codexサブスクで回す。プロジェクト側の推論
費用ゼロ。**これが普及の主レーン。**「あなたが既に払っているモデルに、
ゲームを与える」。結果はローカル完結、信頼は不要。個人設定の影響を排除した
official clean run とは主張しない。

### レーンB: コミュニティ台帳(未検証部門)
自分の対局ログ(events.jsonl+manifest)をPR提出。CIが決定論リプレイ
検証(構造の正しさ)を通す。ただし**「本当にそのモデルが指したか」は
原理的に検証不能**(人間が代打ち可能)なので、speedrun.comの
コミュニティボード同様「未検証部門」と明示する。正直さが信頼を作る。

### レーンC: 公式検証済みラン
メンテナー(または信頼できる実行者)がAPI、またはpersonal customizationを
fail-closedで無効化したCLI profileで実行し、完全なマニフェスト
(モデルID・パラメータ・CLI/harness version・トークン・費用)を記録。少数精鋭。
**公式リーダーボードと対外的な数値主張はここからのみ出す。**
費用は当面小さく(パイロット規模)、可視性が出た段階でラボの
評価クレジット枠やスポンサーが現実的な調達先。

### Harness Lab の参加設計
中央実行、declarative pack、任意コードの受け入れ範囲は未決定。
初期は運営所有の H0〜H2 controlled ablation とし、投稿形式や中立 scheduler は
実測後に決める。候補と未決定事項は
[Harness Lab 方向性](harness-lab-direction-ja.md)を参照。

## 3. リポジトリと配布物

現状の問題: pilot/はローカル専用で、エンジンを製品チェックアウトの
絶対パスで参照している。公開形は:

```
laplacebench(公開リポジトリ)
├── packages/engine      ← game-sharedの凍結コピー or npm参照
│                          パッケージ版 = ルールセット凍結の実体
│                          (laplace-engine-8x8-v1)
├── packages/cli         ← 現pilot/を昇格。npx laplacebench
├── skills/              ← 分析・戦略フォーマット等(競技の提出単位)
├── runs/community/      ← PR提出された対局(CI検証つき)
├── docs/                ← ルールブック、方法論、FINDINGS
└── web-embed仕様        ← 観戦ページとのイベント契約
```

- **エンジンのnpm化がルール凍結を兼ねる**: バージョン番号=ルールセットID。
  適合性テストをパッケージのCIに常設
- CLIは `claude`/`codex` CLIを自動検出。キー無しで段2が成立する
- 観戦UIは製品Webアプリ(/bench)に置き続け、公開デプロイに載せる
  (決定点D1参照)

## 4. 観戦UI v2(「見る」の磨き込み)

現状のv1(一覧+リプレイ+統計バナー)から上げる優先順:

1. **着手根拠の実況表示**: 各手で公開用に生成した着手ノートと、安全な
   テレメトリを同期表示。private reasoning / chain-of-thought は求めず、
   復元せず、表示もしない
2. **共有カード**: リプレイURLごとのOG画像(製品に既存のOG基盤あり)。
   1局=1URL=1枚の絵、がSNS拡散の単位
3. **ランディング**: 自動再生のヒーロー対局+一行の定義+3つのCTA
   (見る/回す/提出する)
4. **ドラッグ&ドロップ再生**: 公開ビューワーにローカルのreplay.jsonを
   落とすと再生(クライアント完結、アップロード不要)。段3の要
5. ブランダーカム(評価急落クリップ)、ライブ観戦(SSE)は後段

**学習シリーズビュー**(実装済み、`/bench/learning`)は Model Arena の
優先順から外す。見せているのはモデル単体ではなく学習ハーネスの効果なので、
Harness Lab の先行資料とする。ただし、Harness Lab タブの比較契約が未実装の間は
深いリンクのまま置く。

## 5. フェーズ計画

### Phase 1: 土台(いま〜)
- リポジトリ抽出、エンジン凍結パッケージ、`npx laplacebench` 化
- 公開デプロイに/benchを載せ、ヒーロー対局(Fable対GPT-5.6等)を掲載
- ドラッグ&ドロップ再生、README/ルールブック/方法論の公開文書
- 出口条件: 「リンクを踏んで観戦→npxで自分の初対局」が他人の環境で通る

### Phase 2: コミュニティ(土台の後)
- PR提出+CI検証+コミュニティ台帳ページ
- 思考実況・共有カード
- 段2〜4の英語・日本語ドキュメント整備、告知(デモ動画+リプレイURL数本)

学習シリーズビューは §4 の通り優先順から外す(実装済み、深いリンクのまま)。

### Phase 3: モデル部門の拡張と公式レーン
- 公式検証済みランでモデル部門リーダーボード初版(API、複数ペア)
- **新種目の検討**: モデル側の候補条件を評価して1つ選ぶ。現時点の最有力候補は
  `split-ally`(同盟の色ごとに独立コンテキスト。味方への意思共有能力を測る。
  [experiment-axes-ja 軸4](experiment-axes-ja.md))だが、実施が確定した
  項目ではない
- 製品アプリに人間対LLM対戦を接続(「フロンティアモデルに挑戦する」
  導線。製品側への最強の還流)

### Harness Lab(方向設計中)

- 別タブでの同一モデル controlled ablation を第一歩とする。Harness Lab 全体では
  各陣営のモデルを選択でき、同じモデルも異なるモデルも対戦可能にする。
- 将来的に harness × model ペアを登録し、人対人のエージェント代理対戦に
  発展する案は残す。
- season、アカウント、プロンプトパック、中央実行の仕様はまだ決めない。
  [Harness Lab 方向性](harness-lab-direction-ja.md)の論点を実測後に更新する。

### Phase 3+: 製品資産との本格統合(ビジョン)

- **オープンアリーナ+ランキング**: 誰でも自分のモデル/設定を持ち込んで
  測定でき、結果がランキング表示される常設アリーナ。信頼レーン
  (自己申告/検証済み)をランキング上で明示的に分離するのが条件。
  Phase 2のスタンディング表示はこの種

## 6. 決定点(要判断)

- **D1: 観戦の公開場所** — 製品Webの既存デプロイに/benchを載せる
  (推奨: 新インフラゼロ、製品への導線にもなる)か、ベンチ専用サイトを
  別に立てるか
- **D2: エンジンの公開形態** — npm公開(推奨: 凍結IDが公的になる)か、
  公開リポジトリへのベンダリング(コピー)か。製品コードの公開範囲の
  意思決定を含む
- **D3: 公開リポジトリの場所と名前** — 新規 `laplacebench` リポジトリを
  GitHubに作るか、既存モノレポ内で公開するか

## 7. 誠実さの原則(公開時に明記するもの)

- 未検証部門と検証済み部門を集計上は絶対に混ぜない
- サブスクCLI経由の対局は「ハーネス込み条件」とラベルする
- 代打ち・モデル差し替えは未検証部門では検出できないと明記する
- 全対局の盤面、公開着手ノート、レフェリーで再検証できるログ、安全な
  テレメトリを公開する。private reasoning / chain-of-thought と secret を含む
  provider payload は公開対象から除外・redactする

### 表現の原則(2026-07-21 追記)

区別は方法論の問題であって、コミュニティへの不信の表明ではない。
UI上の扱いは次の通りにする:

- **「未検証」を目立たせない。** コミュニティの対局は普通のものとして
  表示する。負のバッジ・警告色・大きな注意書きは付けない
- **検証済みの側にだけ静かな正のマーカー**(小さな ✓ verified)を付ける。
  区別は「特別なものに印がある」方向で表現する
- 明記は脚注と方法論ページのレベルで行う(集計の分離という実質は
  維持したまま、視覚的な主張は最小にする)
