# LaplaceBench 実験軸の整理

作成: 2026-07-21。パイロット(判別力確認)完了後のブレインストームを体系化した
もの。[benchmark-strategy-ja](benchmark-strategy-ja.md) と
[design-v0.1](design-v0.1.md) を前提とし、条件は**絶対にラベルなしで混ぜない**
という既存原則の下で運用する。

## 現在のスコープ (2026-07-27 更新)

本ベンチマークは**モデルのベンチマーク**である。採点される比較で動かす変数は
モデルだけで、ルールブック・観測・プロトコル・リソース方針・レフェリーは全員
共通。アダプターはプロバイダが要求する範囲で異なる(Claude CLI 対局と Codex CLI
対局は同一アダプターにできない)ため、各side のアダプターとエフォートは明示され、
ラベル付きの条件として保持する。この文書の軸のうち、その枠の中にあるのは
**軸1(観測形式)・軸2(コンテキスト条件)・軸4(協調条件)**。
provider公式 built-in prompt はCLI version付き条件として許容できるが、個人の
instructions/settings/plugins等が混入した実行は verified Model Arena に含めない。
clean-room要件は[Harness Lab 方向性 §11](harness-lab-direction-ja.md#11-model-arena-の-clean-room-境界)を参照。

**軸3(エージェント設計)は Model Arena の範囲外**とする。
この境界は維持したまま、2026-07-30 に別タブ **Harness Lab** として
方向設計を再開した。現時点では公開レーンや競技を実装済みとはせず、
許可するハーネス階層と投稿/対戦の論点を
[Harness Lab 方向性](harness-lab-direction-ja.md)に分離して記録する。
軸2の `series-notes` も、教訓の書式と蓄積の設計というハーネス側の変数なので
同じ別スコープに置く。

学習ハーネス(`claude-cli-learn`)はこの別スコープへ一度だけ踏み込んだ
n=4 の探索である。勝敗の変化とメモ設計由来の失敗モードは、ハーネスを
独立に調べる初期動機を与えたが、ハーネス効果や個別要因を立証する規模ではない
([FINDINGS Run 7](../packages/cli/FINDINGS.md))。公開アリーナには載せず、
モデル対モデルの記録とは混ぜない。

## 軸1: 観測形式 (modality)

| 条件 | 内容 | 位置づけ |
|---|---|---|
| `json`(現行) | 盤面文字列 約150-250トークン/手 | **主レール。** 安価・高速・状態追跡を純粋測定 |
| `image` | 決定論レンダラーのPNG 約1,000-1,600トークン/手 | ペア診断トラック |
| `image-nolabel` | 駒の文字刻印なし(色のみ) | 色知覚の単離測定 |
| ブラウザ操作 | クリックで着手 | **別ベンチに完全分離**(ブリーフ§3.3の確定事項)。エージェント身体性枠 |

- 仮説A: 挟みの脅威・中央の形は視覚ゲシュタルトの方が見えやすく、**画像で強くなる**モデルがある
- 仮説B: 精密な座標読み取りが弱く、**画像で崩れる**モデルがある
- Vision−Stateギャップは符号すら事前に不明 → モデル間で逆転すればそれ自体が発見
- レンダラー設計: 駒に文字(R/B/Y/G)刻印で色知覚と空間理解を分離。刻印A/Bで色認識だけを単離

## 軸2: コンテキスト条件 (context)

design-v0.1 §3.4 Context Lab の拡張。

| 条件 | 内容 | 測るもの |
|---|---|---|
| `cold`(現行) | ルールブックのみ・毎試合新規 | 初見の強さ(ゼロショット) |
| `primed` | 開始時に戦略ガイド注入 | 知識利得。ガイドは自己対戦から自動生成も |
| `series-transcript` | 連戦で全文脈持ち越し | 生の蓄積能力 |
| `series-notes`(Harness Lab) | 対局後に教訓を自筆させ次戦冒頭に注入 | 蒸留・記憶設計の能力。**書式の設計が主変数なので軸3/Harness Lab側** |

- **スコープ**: `cold` / `primed` / `series-transcript` は文脈の与え方を変える
  だけなのでモデルの能力測定に留まる。この軸で現在生きているのはこの3条件
- **「初見の強さ」と「蓄積で伸びる力」は別能力** → 蓄積側を測るなら
  `series-transcript`(生の持ち越し)で測る。実装コストは小さい(アダプターに
  シリーズモード追加のみ)
- リーダーボードを2枚に割る案(コールドスタート順位と学習スロープ順位)は、
  `series-notes` を Model Arena に混ぜる前提だったため採用しない。
  learning harness の集計単位と初期状態は Harness Lab の未決定論点。
  `series-transcript` だけで学習スロープを意味のある指標にできるかは未検証

## 軸3: エージェント設計 (harness engineering) — Harness Lab 方向設計

> **状態: 2026-07-30 に別 Harness Lab として方向設計を再開。**
> Model Arena の採点対象をモデル対モデルに絞る境界は変えない。
> 以下は保留時の設計記録で、現在のタブ、許可階層、投稿/対戦論点は
> [Harness Lab 方向性](harness-lab-direction-ja.md)を正とする。

**controlled comparison ではモデルを固定し、人間が組むエージェント設計を
変数にする。** Harness Lab 全体はモデル固定ではなく、各陣営が harness × model
ペアを選べる。同一モデル戦は「組み方でどれだけ差がつくか」、異モデル戦は
分解不能なシステム総合戦として表示・集計を分ける。

設計の変数の例:

- 候補手を出させて**フレッシュなエージェント同士に議論・投票**させるskill
- 着手前の**合法性セルフチェック**サブエージェント
- **メモの設計**: 何を残すか、どう構造化するか(軸2のseries-notesの自由化)
- **事前準備**: 自己対戦で戦略書を作ってから本番に臨む
- 探索的な構成: LLM評価つきの浅い木探索、役割分担(偵察役/計画役)

### 任意の fixed-model division が持つ新規性

Halite/Battlecode/Screeps/AIWolf等の「同じゲーム、あなたのコード」系
プログラミング対戦の系譜に、Harness Lab の1部門として
**「固定されたフロンティアモデル、あなたのオーケストレーション」**という
新形式を持ち込める。これは全 Harness Lab の定義ではなく、ハーネス差を
読みやすくする fixed-model division である。LLM以前には
存在し得なかった競技であり、次の含意を持つ:

1. **人対人のエージェント代理対戦。** 名前を持つ人間の設計同士が戦う。
   モデル比較ベンチを超えて、観戦・実況・コミュニティリーダーボードが
   成立する(配信・共有と最も相性が良いのはこのディビジョン)
2. **エージェント工学の実験場。** どの設計パターン(議論/検証/記憶形式)が
   汎化するかという、それ自体発表価値のある知見が対戦データから出る
3. **提出インターフェースは既に存在する。** design-v0.1の
   `persistent-agent` 条件と adapter仕様(start_game/act/end_game +
   リソース上限)が、そのまま提出フォーマットになる。パイロットの
   `Agent` インターフェースはその実装済みの雛形

### fixed-model division の公平性ルール案

- この division 内だけモデルとエフォートを固定(例: 全員 sonnet@medium)
- 1試合あたりの**総トークン/費用バジェット**で揃える(内部構成は自由)
- 全モデル呼び出しをログ(規定外モデル使用の検出)
- レフェリー・観測・失敗ポリシーは共通

### 先行探索で得た示唆

当初は「素のアダプター vs 議論・合法性チェック付きアダプター」を1ペア走らせて
差が出ることを示す計画だった。実際には学習ハーネス(`claude-cli-learn`)の
learn-vs-cold 4局が近い問いを探索した。同一モデル・同一エフォートで勝敗に
差が出たほか、座席ラベル依存のメモと攻撃偏重の蒸留という、メモ設計由来の
失敗モードが観測された。ただし n=4 なので、ハーネス効果や個別要因の因果を
結論づけない。Harness Lab の存在意義を検証する動機と、次の controlled
ablation で確かめるべき仮説を得た段階である。

## 軸4: 協調条件 (coordination)

**1つの頭脳が2色を運用する現行条件に対し、同盟の2色を切り離す。**

| 条件 | 内容 | 測るもの |
|---|---|---|
| `single-mind`(現行) | 1モデル・1コンテキストが Red+Yellow を担当 | 2軍同時運用の計画能力 |
| `split-ally`(**候補**) | 色ごとに独立コンテキスト・独立スレッド。同盟間で私的状態を共有しない | **味方への意思共有能力**。盤面から読み取れることと、レフェリーが運ぶことを許した情報だけで連携できるか |

- 現行条件では「協調」は自分の頭の中で完結しており、伝達能力は測れていない。
  切り離すと初めて、**思考を読めない相手と方針を揃える**能力が分離される
- 相手チームと私的コンテキストを共有しない原則(design-v0.1 §3.4)はそのまま。
  切るのは**同盟内**であって対戦相手側ではない
- 設計上の未決: レフェリーが同盟間に何を運ぶか(何も運ばない / 直前の着手のみ /
  短い公開メッセージ)。`public-dialogue` と混ぜない
- 結果は base 条件と絶対に合算しない。別種目として扱う

## 優先度の推奨

1. **軸1 Visionペア**: 公開時の主役。レンダラー実装が必要
2. **軸2 シリーズ蓄積**(`series-transcript` まで): 実装最小・無人で回る
3. **軸4 `split-ally`**: モデル側の新種目として最も新規性がある候補
4. 軸3(ハーネス部門): Model Arena とは別に Harness Lab の方向設計を進める。
   ブラウザ操作版は引き続き保留
